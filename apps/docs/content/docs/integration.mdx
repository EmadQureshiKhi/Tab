Three ways to put an Agent on the rail, and three to put a Service on it, in the order most people should try them.

The MCP server is the shortest path and needs one line of configuration.
The CLI is what writes that line.
The server plugins are what a Service meters through.
The payment-strategy seam is the one you reach for when your Agent signs with something other than a plain key, and it is deliberately small.

Everything on this page runs as written against the hosted Testnet deployment.
For Mainnet, set `MONAD_CHAIN_ID=143` and use the Mainnet addresses and gateway from the [introduction](/#where-it-runs).

## Install

```bash
npx -y @tabai/sdk connect
```

That is the whole adoption step.
It finds your client's configuration file for your platform, backs the file up, merges a single `mcpServers.tab` entry, and prints the diff before it writes.
It knows `claude-code`, `claude-desktop`, `cursor`, `windsurf` and `vscode`, and takes `--client <id>`, `--config <path>` or `--dry-run`.
Run it twice and the second run writes nothing: the merge is idempotent, and it leaves no second backup.

**It never writes a private key.**
Signing keys are read from the environment when a Settlement is broadcast or a metered call is signed, and nothing about them is copied into a client configuration file.
Set `AGENT_ADDRESS` before running it and the entry carries the Agent too.
The hosted gateways meter only a signed call, so for `tab_call` the environment the client launches the server with also needs `AGENT_PRIVATE_KEY`.
Check the whole installation, keylessly, with:

```bash
npx -y @tabai/sdk doctor
```

`doctor` reports what it could reach and warns rather than passing on what it could not.
A missing Agent address is a warning and not a failure, because the read-only tools work without one.

## The command line

The same package is a CLI.
Every command reads the chain; one of them writes to it, and it says so before it does.

| Command | What it does | Spends |
| --- | --- | --- |
| `connect` | Writes the `tab` entry into your MCP client's configuration | nothing |
| `mcp` | Serves the four tools over MCP. This is what a client launches | nothing |
| `doctor` | Checks the installation against the live deployment | nothing, and needs no key |
| `status` | What an Agent owes, may still spend, and has settled | nothing, and needs no key |
| `settle` | Pays down an Open Tab, with the Agent's key or, with `--strategy monad-relayed`, by a Permit2 signature the gateway submits | real funds, and only with `--broadcast` |

`settle` is a dry run unless you ask otherwise.
It needs a payment strategy, so run it with the `tab.config` below and `AGENT_PRIVATE_KEY` set.
It checks that the Service accepts the Asset, quotes the amount, and stops:

```bash
npx -y @tabai/sdk settle \
  --agent 0x1f6f…0542 \
  --asset 10143:0x4802…4083 \
  --service 0x7461…0000 \
  --amount 47000
```

```
Dry run. Nothing was broadcast.
  chain id    10143
  amount      47000

Add --broadcast to send it. This spends real funds.
```

Amounts are always base units.
USDC has six decimals, so `47000` is 0.047 USDC.
Nothing in this system takes a decimal, holds a price, or consults a rate.
On Testnet the mock token is named `mUSDC` wherever a symbol is printed, so a receipt in it is never mistaken for one in Circle's USDC.

`mcp` serves over stdio by default, and over streamable HTTP with `--http [--port <n>] [--host <h>] [--endpoint <p>]`.

## tab.config

With nothing configured, the SDK reads the hosted registry read API for the chosen network and knows the hosted demo Service, `tab.demo`, at its hosted gateway.
Both are exported as `TAB_HOSTED`, anything you configure takes precedence over them, and `TAB_HOSTED_DEFAULTS=off` switches them off for a setup that must reach nothing it did not name.
The hosted gateway meters only a signed call, so with `AGENT_ADDRESS` and `AGENT_PRIVATE_KEY` set and no file at all, `tab_call` reaches `tab.demo` and signs each call with the Agent's own key.

A file is for everything beyond that: the Agent's address if you would rather not put it in the environment, any Services beyond the demo one (the chain records no URL for a Service), the payment strategies, and the x402 signer.

A `tab.config.mjs` beside your project, or any parent directory:

```js
import { Wallet, JsonRpcProvider } from "ethers";
import { agentSignedMetering, createMonadStrategy, createRelayedMonadStrategy } from "@tabai/sdk";

const assets = {
  "10143:0x480209747417f5c830fda188a9b9acfa70bc4083": {
    chainId: 10143n,
    address: "0x480209747417f5c830fda188a9b9acfa70bc4083",
    decimals: 6,
    symbol: "mUSDC",
  },
};

// The Agent's signer, or nothing. Built only when something has to sign.
const agentSigner = () =>
  process.env.AGENT_PRIVATE_KEY === undefined
    ? undefined
    : new Wallet(process.env.AGENT_PRIVATE_KEY, new JsonRpcProvider(process.env.MONAD_RPC_URL));

export default {
  // Whose Open Tab a metered call lands on.
  agent: process.env.AGENT_ADDRESS,

  // The chain records no URL for a Service, deliberately, so the address lives here.
  // tab.demo is known without this entry; it is spelled out to add the Hub.
  services: [
    {
      serviceId: "0x7461622e64656d6f000000000000000000000000000000000000000000000000",
      name: "tab.demo",
      endpoint: "https://gateway-testnet-production-a657.up.railway.app",
      // The gateway meters only a signed call; the Agent signs its own.
      headers: agentSignedMetering(agentSigner),
      // The API Hub provider this Service fronts on credit. tab_discover lists
      // its endpoints under the Service, priced by the Hub.
      hub: { provider: "defillama", prefix: "apihub" },
    },
  ],

  // The x402 signer for the prepaid fallback: when a Service refuses a call on
  // credit and its 402 carries an x402 offer, tab_call pays for that one call.
  // Leave it out to never prepay.
  x402: agentSigner,

  // Factories, not objects: a signer is built only if something settles, so
  // every read stays keyless. The direct path first; the gasless one is taken
  // by id (--strategy monad-relayed) or when the direct one declines.
  strategies: [
    () => {
      const signer = agentSigner();
      if (signer === undefined) return undefined;
      return createMonadStrategy({ signer, tabSettlement: process.env.TAB_SETTLEMENT_ADDRESS, assets });
    },
    () => {
      const signer = agentSigner();
      if (signer === undefined) return undefined;
      return createRelayedMonadStrategy({
        signer,
        tabSettlement: process.env.TAB_SETTLEMENT_ADDRESS,
        relayUrl: "https://gateway-testnet-production-a657.up.railway.app/relay/settle",
        assets,
      });
    },
  ],
};
```

The key is read from the environment at the moment a Settlement or an x402 payment is built, and never from this file.
`tab_discover`, `tab_status` and `doctor` never call a factory, which is what keeps every read on this rail keyless.
The relayed strategy needs one `approve(Permit2, amount)` on the Asset before its first use, and names that approval in its refusal when it is missing.

**A factory may decline.**
Returning `undefined`, as the one above does when no key is set, means "not available here" rather than "this config is broken": the strategy is skipped and everything else in the file stands.
That is the whole reason the entry is a factory rather than an object, and it is what lets one config file serve a read-only process and a settling one without branching.

With that file in place, `AGENT_ADDRESS` and `MONAD_RPC_URL` set and `connect` already run, the one warning `doctor` leaves is the missing signing key.
Supply `AGENT_PRIVATE_KEY` and it reports none.

## As a dependency

`connect` is for a client.
To build against the rail directly:

```bash
npm install @tabai/sdk
```

```ts
import { createTabToolset, createTab402Client, createMonadStrategy, createRelayedMonadStrategy } from "@tabai/sdk";
```

The package ships its own types and carries no workspace dependency, so it installs and type-checks on its own.
Beside the main entry point, `@tabai/sdk/hub` (the API Hub manifest reader) and `@tabai/sdk/metering` (the metering-signature digest) are pure entry points for a bundle that must not carry the `tab.config` file walk.

| `tabPostPaid`, `honoTabPostPaid`, `expressTabPostPaid`, `withTabPostPaid` | Server plugins that meter a route after it has already responded |

| `createMonadStrategy`, `createStrategyRegistry` | The Monad payment strategy, and the registry that resolves strategies |

## The four MCP tools

Each tool declares a JSON Schema for its input and its output, and validates its own input against the schema it published.
**None of them throws.**
A failure returns `ok: false` with an `error` carrying a `category`, a `code`, a `message` and `retryable`, so a model can decide what to do next rather than parse an exception.

| Tool | What it does | Spends |
| --- | --- | --- |
| `tab_discover` | Lists Services, the Assets each accepts, what each tool costs, the Bond each has escrowed, and the API Hub endpoints a Service fronts | nothing, and needs no key |
| `tab_call` | Calls a metered tool. The charge lands on the Open Tab and is settled later. With an x402 signer configured, a credit refusal that carries an offer is prepaid instead, and the output says so | nothing at call time, unless it prepays |
| `tab_status` | The Agent's Credit Limit, Open Tab, prepaid credit and headroom per Asset, with recent Settlements | nothing, and needs no key |
| `tab_settle` | Pays down an Open Tab by sending `TabSettlement.settle` with the Agent's own key, or a Permit2 signature through the relay | real funds |

Start with `tab_discover`, because `tab_call` needs a `serviceId` from its list.

### The failure that matters

An Agent with no headroom is the one case worth handling by name.

```json
{
  "ok": false,
  "error": {
    "category": "LIMIT",
    "code": "LIMIT_EXCEEDED",
    "message": "this call needs 10000 base units and the Agent has 2500 of headroom for the Asset; settle with tab_settle and call again",
    "retryable": false,
    "requiredBaseUnits": "10000",
    "headroomBaseUnits": "2500"
  }
}
```

Both figures are present only on `LIMIT_EXCEEDED`, and they are there so the answer is actionable.
The correct response is to settle, not to retry: retrying a call that exceeded a Credit Limit produces the same refusal at the same cost.
A Settlement restores headroom in the block it lands, so the retry after one succeeds.

`tab_settle` takes `dryRun` for exactly this moment.
It resolves the Service's Collection address, checks the Asset is accepted, and reports what it would broadcast without broadcasting it.

The other answer to a refusal is to pay for that one call.
When the Service's `402` carries an x402 `PAYMENT-REQUIRED` offer and `tab.config` names an `x402` signer, `tab_call` signs an EIP-3009 authorization for the charge, repeats the request with `PAYMENT-SIGNATURE`, and returns the result with an `x402` block naming the transaction.
Nothing lands on the Open Tab, because nothing is owed, and the payment is not a Settlement: it does not enter the credit history and does not raise the limit.
The [On Monad](/on-monad) page has the whole exchange.

### A new Agent starts at the baseline once it authorises a bonded Service

A Credit Limit is capped by the Bonds of the counterparties the Agent has authorised or settled with.
An Agent that authorises a bonded Service starts at `min(baseline, 95% of that Service's free Bond)`.
Anything above the baseline is earned by settled history with at least three Curated, bonded Services.
An Agent that has authorised nobody has no counterparties and no limit.

## Running a metered Service

Deliver first, charge after.
The plugin adds three status codes to your surface: a `402` when a charge would exceed the caller's Credit Limit, and the `403` and `409` below.

```ts
import { honoTabPostPaid, tabPostPaid } from "@tabai/sdk";

app.use("/meter/*", honoTabPostPaid(tabPostPaid({ serviceId, asset, priceOf, tabBook })));
```

Tools are mounted under `/meter/<tool>` off the Service's published endpoint: that is where `tab_call` sends a call, where this repository's gateway serves them, and what leaves `/hub/<prefix>` beside the tools rather than under them.
The handler runs, the response is produced, and only then is the delivered work metered into the Agent's Open Tab with `recordDelivery`.
By default the response is held for that one record and released carrying six charge headers, which go out together or not at all: `Tab-Charge-Amount`, `Tab-Charge-Asset`, `Tab-Charge-Service`, `Tab-Charge-Tool`, `Tab-Open-Tab` and `Tab-Headroom`.
With `release: "before-metering"` the response goes out first and the record lands behind it, which is the shape for a Service that will not accept even one block of latency.

Three refusals reach the Agent, because only the Agent can clear them.

| Status | Revert | What clears it |
| --- | --- | --- |
| `402` | `LimitExceeded` | a Settlement. The body and the headers carry the required amount and the headroom |
| `403` | `AuthorisationMissing`, `AuthorisationExpired`, `AuthorisationExceeded` | a new `TabBook.authorise` |
| `409` | `TabIsDelinquent` | a Settlement that closes the tab |

Every other revert is the Service's fault, and the plugin delivers the handler's own response unchanged rather than handing the cost to the caller.
A Service whose billing is broken pays for the delivery.

A Service may put an x402 offer beside the `402`.
`exactRequirementFor` builds the requirement for the same charge, `paymentRequiredHeaders` puts it on the refusal, and `handlePrepaidRequest` answers a request that comes back carrying `PAYMENT-SIGNATURE`: verify through the facilitator, deliver, settle through the facilitator, answer with `PAYMENT-RESPONSE`.
A payment that does not verify delivers nothing, and a delivery that failed is never settled.
A prepaid request needs no metering signature: it carries its payment, which is what the offer is for.

The metering gateway in this repository is that plugin with two things the SDK cannot know added: which chain to talk to, and who is allowed to ask.
Every metered route requires a signature over a digest of the method, the path, the Agent, the tool, the unit count and a timestamp, because a gateway that holds an operator key and meters unauthenticated requests would let any stranger charge any Agent up to its whole authorisation ceiling.
Two parties may give it.
The Service's own front signs with the operator key in `Tab-Operator-Signature`, having authenticated its caller however it likes.
Or the Agent signs with its own key in `Tab-Agent-Signature`, recovered against `Tab-Agent`, which is the shape a gateway on the open internet takes: the one party that pays for the call is the one that asked for it.
`agentSignedMetering` in `tab.config` is the Agent's side of that, one line on the Service entry, and it builds the key only when a call is made.

```js
import { agentSignedMetering } from "@tabai/sdk";

services: [{ serviceId, endpoint, headers: agentSignedMetering(agentSigner) }]
```

Before it broadcasts, the gateway proves the witness against `TabBook.historyCommitment` and simulates the call, so a delivery that would revert is never paid gas for.
The history behind that witness is held between calls and read from the registry's `GET /agents/:agent/witness/:asset` on first sight, so a metered call costs one commitment read and not a log scan from the deployment block.

### The client side of the 402

```ts
import { createTab402Client } from "@tabai/sdk";

const client = createTab402Client({ baseUrl: "https://gateway-testnet-production-a657.up.railway.app", agent });
const result = await client.fetch("/meter/quote.generate");
```

The client sends `Tab-Agent`, parses the same six headers on a success and on a `402` with the same parser, and keeps a running snapshot per Asset of what it has accrued, what was declined, and the headroom the Service last reported.
It repeats a request once after a `402`, never more, because a retry loop against a credit decision is the mistake the figures in the body exist to prevent.
It adds no metering signature, so against a gateway that requires one, such as the hosted `tab.demo`, pass `Tab-Agent-Signature` and `Tab-Agent-Issued-At` in the request headers, or call through `tab_call` with `agentSignedMetering`.
It does not settle on its own.
A `402` that still stands comes back as a `LIMIT_EXCEEDED` result carrying the two figures, and the decision to settle stays with the Agent.

### Metering an upstream you do not control

`createTabProxy` forwards a request to an upstream, meters it on the way back, and runs hooks around it.
A hook is a named pair of optional phases: `before` runs ahead of the forwarded request in registration order, and `after` runs once the response exists in reverse order, the same nesting a middleware stack has.
Every phase returns a `Result`, and a hook that fails is logged and skipped unless it declared `critical: true`, because a Service whose log shipper is down should still deliver work.
A hook that looked a Settlement up on chain can attach it to the request context, with its `settlementId`, `applied` and `toPrepaid` figures straight off the `Settled` event.

### Fronting an x402 upstream on credit

`createX402FrontedProxy` is the reverse of the offer above and the thing that puts Tab on top of pay-per-request APIs.
The Agent calls the Service on credit; the Service forwards to an x402 upstream, reads the price off the upstream's `402`, pays it with its own key, and meters the Agent's Open Tab for that price plus a margin.
The Agent never signs and never holds the upstream's currency.

```ts
import { createX402FrontedProxy, createX402UpstreamPricing, tabPostPaid } from "@tabai/sdk";

const pricing = createX402UpstreamPricing({ tool, margin: { bps: 500n } });
const metering = tabPostPaid({ serviceId, asset, tabBook, priceOf: pricing.priceOf });
const proxy = createX402FrontedProxy({
  upstream: "https://x402.monid.ai/v1",
  stripPrefix: "/hub/apihub",
  signer: operatorWallet,
  asset,
  pricing,
  metering,
  preflight: async ({ agent, amount }) => simulateDelivery(agent, amount),
});
app.all("/hub/apihub/*", (c) => proxy(c.req.raw));
```

`preflight` runs between the upstream's `402` and the operator's signature, with the quoted amount in hand, so an Agent with no headroom is refused before the Service's own funds move.
A fronted tool must be priced on chain like any other, and because its price is not known until the upstream answers, the amount rides in the unit count: the Service publishes one base unit per unit and a call consumes as many as it cost.
An unpriced fronted tool reverts `UnknownTool`, the plugin delivers the work anyway, and the Service pays the upstream and bills nobody.
The API Hub takes USDC on Monad Mainnet and nothing else.
A Mainnet Service pays it on its own chain; a Testnet Service names that chain and Asset in `upstreamPayment` and pays there with a key funded there, while the Agent is metered on Testnet in the Service's own Asset, base unit for base unit.
The metering gateway mounts the API Hub at `/hub/apihub` and Nansen at `/hub/nansen` from `GATEWAY_HUB_UPSTREAMS`, each with a `payOn` naming Mainnet USDC, and `tab_discover` lists a fronted provider's endpoints from the Hub's manifest.

### Relaying gasless Settlements

`POST /relay/settle` on the gateway takes the body `createRelayedMonadStrategy` produces: the Agent, the Service, the Asset, the amount, a nonce, a deadline and the Permit2 signature.
It checks the chain and the surface, simulates `settleWithPermit2` from the operator, maps every revert to a named refusal (`PERMIT_SIGNER_MISMATCH`, `PERMIT_NONCE_USED`, `PERMIT_EXPIRED`, and the contract's own), and only then submits and waits for the receipt.
The reply carries the transaction hash and the `settlementId`, `applied` and `toPrepaid` figures off the `Settled` event, the same receipt the direct strategy returns.
The relayer pays gas and holds nothing: the Asset moves from the Agent to the Collection address inside the Settlement, exactly as it does on the direct path.

## The payment-strategy seam

On Monad a tab is paid through `TabSettlement`, by `settle` with the Agent's key or by `settleWithPermit2` with its signature, and the shipped strategies do one each with an `ethers` signer.
The seam exists so that a different signer, a smart account, a session key, or a test double can stand behind the same call without the SDK caring which.
`createKuruFundedStrategy` shows the seam used the other way: it wraps a strategy and tops the Agent's balance of the Asset up through Kuru before delegating.

A strategy is five members and an optional sixth:

```ts
export interface PaymentStrategy {
  readonly id: string;
  readonly chainIds: readonly bigint[];
  supports(asset: AssetRef): boolean;
  quote(request: ChargeRequest): Promise<Result<ChargeQuote>>;
  settle(request: SettleRequest): Promise<Result<SettlementReceipt>>;
  settleBatch?(requests: readonly SettleRequest[]): Promise<Result<readonly SettlementReceipt[]>>;
}
```

A receipt carries the transaction hash and, once the receipt is read, the `settlementId`, `applied` and `toPrepaid` figures from the `Settled` event.
`settleBatch` maps onto `TabSettlement.settleBatch`, which pays several tabs in one transaction, and it should stay undefined where the signer behind the strategy has no batch form.

### A strategy over a different signer

```ts
import { createMonadStrategy, createStrategyRegistry } from "@tabai/sdk";

const sessionKeyStrategy = createMonadStrategy({
  signer: mySessionKeySigner,     // anything with an ethers Signer's shape
  tabSettlement: process.env.TAB_SETTLEMENT_ADDRESS,
  assets,
});

const registry = createStrategyRegistry([sessionKeyStrategy]);
```

`quote` never converts.
Tab records integer base units of one Asset and holds no price, rate or oracle anywhere, so a quote is the request's own amount handed back.
Nothing here returns a boolean for success.
Every fallible call returns a `Result`, and a strategy that throws will take down the caller that trusted it.

## Environment

The full contract is `.env.example` at the repository root, which is checked against every `process.env` read in the tree, so it cannot drift.
An integrator needs a much smaller set than a developer does.

| Variable | Needed for |
| --- | --- |
| `MONAD_RPC_URL` | `doctor`'s chain checks, and the provider a signer in `tab.config` sends through. The MCP tools read through the registry read API and need no RPC |
| `MONAD_CHAIN_ID` | `143` for Mainnet, `10143` for Testnet. Defaults to Testnet |
| `MONAD_EXPLORER_URL` | the links a page or a receipt prints. Never read by the contracts or the SDK's chain calls |
| `TAB_BOOK_ADDRESS`, `TAB_SETTLEMENT_ADDRESS`, `SERVICE_REGISTRY_ADDRESS`, `BOND_ADDRESS` | resolving credit, Services and Bond |

| `NEXT_PUBLIC_REGISTRY_API_URL` | the Service directory and the Agent's history. Defaults to the hosted read API for the chosen network |
| `TAB_HOSTED_DEFAULTS` | `off` stops the hosted read API and demo Service from filling in what you did not configure |
| `AGENT_ADDRESS` | the Agent `tab_call` meters against, when `tab.config` names none. Public, so `connect` copies it into the MCP stanza |
| `AGENT_PRIVATE_KEY` | broadcasting a Settlement, signing a Permit2 witness, paying an x402 offer, or signing a call to the hosted demo Service, and nothing else. Never written to a configuration file |

The deployed addresses were read back off the chain by a script that holds no key, so they are checkable by anyone with an RPC endpoint rather than only by whoever deployed them.

## What the rail refuses

The refusals that matter to an integrator are these: `revertMappingFor` classifies the `recordDelivery` ones, and the gateway's relay names the Permit2 ones.

| Revert | Where | What it establishes |
| --- | --- | --- |
| `NotSettlementSurface` | `TabBook.applySettlement` | nothing but the wired `TabSettlement` can lower a tab |
| `PriceListChangedMidCall` | `recordDelivery` | a Service cannot quote one price and meter another |
| `AuthorisationExceeded` | `recordDelivery` | a Service cannot meter past the ceiling the Agent set |
| `HistoryCommitmentMismatch` | any limit read | a witness with a record added, dropped or edited is refused |
| `IneligibleBondEntry` | any limit read | a witness cannot cite a Bond the Agent has no relationship with |
| `SettlementWindowOpen` | `markDelinquent` | a tab cannot be marked before its window has closed |
| `InvalidSigner`, `InvalidNonce`, `SignatureExpired` | `settleWithPermit2`, from Permit2 | a Permit2 witness is single-purpose: the wrong signer, a spent nonce or a passed deadline is refused before anything moves |

Of those, only the authorisation ceiling is the Agent's to raise.
The rest are the Service's, and where one of them stops a delivery from being metered the plugin delivers the handler's response anyway.
